# ai-profile v0.7.0 Automation Layer Implementation Plan

> **For Codex:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Ship the v0.7.0 automation layer: a batch `aiprofile refresh --out DIR [--dry-run]` application service that re-scans every configured repository and republishes the exact eight-file dist bundle with fail-closed pre-publication behavior and residual-honest incomplete rollback; a stdlib-only `aiprofile schedule install|status|remove` command with narrow Windows Task Scheduler / macOS launchd / Linux systemd-user adapters driving a single-instance launcher that refreshes, stages exactly the eight dist paths, commits only those paths and only on byte change, and pushes by default with an explicit non-force push to the branch and remote recorded at install time; and a public-only reusable GitHub Actions workflow (package version and destination hard-coded per release tag) plus a copyable caller template for users whose scanned repositories are all public. All default output — refresh stdout/stderr, lock errors, scheduler CLI errors, and the scheduler's last-run log — identifies repositories by config ordinal and aggregate counts only: no paths, no repository names, no basenames (local `refresh -v` may expose chained detail and is never enabled in public automation). The maintainer Profile keeps using the local scheduler (its config includes an `aggregate_only` repository, which the public Action must never scan). No ACE schema, aggregation, `VizStats`, renderer, or eight-output contract change of any kind.

**Architecture:** Two new application-layer modules above the existing pipeline, plus one workflow pair. `src/aiprofile/lockfile.py` provides a cross-platform nonblocking per-`AIPROFILE_HOME` advisory lock (msvcrt on Windows, fcntl elsewhere). `src/aiprofile/refresh.py` is an orchestration service in cli.py's layer: it may import `scanner`, `aggregate`, `privacy`, `render.*`, `export`, `config`, `schema`, `storage`, `viz`, `errors`, `lockfile` — renderers and exporters stay pure and keep consuming validated `VizStats` only; refresh adds no new render or privacy behavior, it sequences existing behavior (scan all → aggregate once → render once → `export.write_outputs` once). Dry-run builds a shadow home under the already-held home lock: `config.json` is copied, and the database is snapshotted with sqlite3's online backup API (`Connection.backup()` from a read-only source connection into a fresh shadow-path connection) so committed WAL content is included — never a raw copy of the main DB file alone; configuration, publication policy, recorded DB/WAL content, and output assets remain unchanged, while the advisory lock and transient SQLite `-shm` coordination bytes are explicit non-data exceptions. `src/aiprofile/schedule/` holds the CLI service (`service.py`), the launcher payload writer (`launcher.py` template written under `AIPROFILE_HOME/scheduler/`), and per-OS adapters (`adapters/windows.py`, `adapters/launchd.py`, `adapters/systemd.py`) that only build argv lists and file payloads — all process execution goes through `subprocess.run(list, shell=False)`; nothing is ever interpolated into a shell string. Every adapter derives its task, label, or unit name from an opaque digest of the canonical `AIPROFILE_HOME`, so different homes cannot overwrite or remove one another's registration. Windows registers via a Task Scheduler XML definition (`schtasks /Create /XML`, separate `Command`/`Arguments`, LeastPrivilege current-user interactive token, `MultipleInstancesPolicy=IgnoreNew`, `StartWhenAvailable=true` — never a fragile `/TR` command string); launchd serializes its plist with stdlib `plistlib.dumps`. `schedule install` refuses a detached HEAD, records the profile repo's current branch and remote name (names only — never URLs or tokens), and captures the prior native status before mutation so rollback never creates or activates a registration that did not previously exist. The launcher and management commands share `AIPROFILE_HOME/.schedule.lock`, refuse branch or captured-HEAD drift, then build an exact-eight-path tree through a temporary Git index under `AIPROFILE_HOME/scheduler/` (confined by a tool-owned POSIX `0700` directory and reset to `0600` after each Git operation; inherited user-home ACL on Windows). Git may transiently apply the repository's shared-file mode to an index rewrite, while Git object creation keeps the repository's ambient permission policy. `git commit-tree` returns the scheduler-created OID directly, and `git update-ref refs/heads/<recorded branch> <commit OID> <captured HEAD OID>` atomically advances the branch only if it still has the expected value; the real index is then synchronized for only those eight paths, preserving unrelated staged entries. The captured commit is pushed immutably with explicit non-force `git push <recorded remote> <captured commit OID>:refs/heads/<recorded branch>`; `--no-push` still creates and advances this local commit but skips the remote push, and no SHA is logged. Plumbing deliberately bypasses repository commit hooks and signing so an unattended refresh never executes repository-provided hook code. `.github/workflows/profile-refresh.yml` is a `workflow_call`-only reusable workflow (public repos only; validated public repository identifiers as the ONLY input; identities as a required secret; ephemeral home in `RUNNER_TEMP`; the released PyPI version `0.7.0` and the caller destination `dist` hard-coded inside the workflow so the caller controls neither; split read-only build job / least-privilege commit job; exact immutable `published-sha` output). `docs/templates/profile-refresh-caller.yml` is the copyable caller pinned to the full 40-hex commit A SHA, with a non-top-of-hour schedule, `workflow_dispatch`, caller-level concurrency spanning refresh through deploy, and a separate least-privilege Pages job that checks out exactly `${{ needs.refresh-profile.outputs.published-sha }}` and publishes `_site/dist` containing the exact eight outputs. Static workflow-contract tests in the style of `tests/unit/test_release_workflow_contract.py` / `test_staging_preview.py` pin every guardrail.

**Tech Stack:** Python ≥ 3.11 stdlib only (no new runtime dependencies: `msvcrt`/`fcntl`, `subprocess`, `argparse`, `json`, `sqlite3` `Connection.backup()` for the dry-run DB shadow, `plistlib` for the launchd plist — no hand-written XML templates or `xml.sax.saxutils.escape` anywhere; the Windows task definition is built with `xml.etree.ElementTree`), system `git` ≥ 2.17, `schtasks.exe` / `launchctl` / `systemctl --user` invoked via argv, pytest + Ruff, GitHub Actions with all official actions pinned by full commit SHA (reuse the exact pins already in `.github/workflows/ci.yml`; the Pages trio in the caller template uses the current verified pins listed in Task C2).

Local `refresh -v` may expose chained detail; public automation never enables it. Scheduler output remains fixed/path-free.
- **Pre-commit review sequence (MANDATORY for every commit, before `git commit` runs):** (1) Codex independently reviews the UNCOMMITTED diff; (2) the code-review skill AND the code-reviewer subagent both run on that same uncommitted diff; (3) every finding is fixed (code fixes red-first) and re-reviewed until clean; (4) only Fable stages and commits — staging is explicit per-path `git add <path>` with a `git diff --cached --name-only` count assertion (never `git add .`/`-A`), and the commit carries the repo's AI trailer block (AGENTS.md "Commit trailers"): blank line before the block, no blank line inside it. The FIRST review always happens on the uncommitted diff before the commit exists — never deferred until after push. After commits exist: push the PR branch, wait for green CI, then the committed-range independent gate review (Task E3) before merge.

### Task B2: launcher git publication — exact 8 pathspec, change-gated commit, push/no-push

**Files:** `src/aiprofile/schedule/launcher.py`, `tests/unit/test_launcher.py`, `tests/integration/test_scheduler_launcher.py` (new).

The exact eight staged paths are `dist/<name>` for the eight allowlisted names — import the name set from `aiprofile.export` so the two allowlists cannot drift (add a public `PUBLIC_ASSET_NAMES` re-export in `export.py` = `_ALLOWED_ASSET_NAMES | {"profile.json"}`; pure rename-level change, no behavior).
